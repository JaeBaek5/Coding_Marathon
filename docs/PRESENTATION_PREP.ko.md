## 1. 한 줄 소개

머먹은 사용자의 **자연어 요청**과 **구조화된 위치**를 바탕으로, OpenRouter 기반 멀티 에이전트가 식사 조건을 이해하고 **네이버 맛집·경로·리뷰 근거**를 조합해 **한 번에 하나씩** 식당을 추천하는 모바일 우선 웹앱입니다.

## 3. 평가기준 예상표

| 항목 | 예상 비중 | 심사 포인트 | 머먹 대비 |
| --- | ---: | --- | --- |
| 주제 적합성 | 15~20 | OpenRouter 기반 AI 서비스인지 | 역할별 모델 + Bet 리뷰 적합도 LLM |
| 문제 정의 명확성 | 10~15 | 해결 문제가 선명한지 | “상황에 맞는 한 끼 선택” |
| 기술 완성도 | 20~25 | 실제 동작, 안정성 | 입력 → 질문 → 추천 → 피드백 → 작동 로그 |
| 창의성/차별성 | 15~20 | 단순 챗봇과 다른지 | 음식 카탈로그·상태 기반 음식 맞추기·규칙+AI 랭킹 |
| 실용성/확장성 | 10~15 | 실제 사용 가치 | 학생/직장인 점심·해장·술자리 시나리오 |
| 발표/질의응답 | 15~20 | 10분 안에 이해되는지 | 구조·데모·랭킹 원칙·한계 |

고득점 우선순위:

1. 데모가 끊기지 않는 핵심 흐름
2. “챗봇 한 방”이 아닌 **에이전트 + deterministic 랭킹** 차별성
3. OpenRouter **역할별 모델** 근거
4. **음식·리뷰 우선** 랭킹 설명 (가까운 곳 ≠ 1등)

## 4. 핵심 메시지

- 머먹은 맛집 **목록 앱**이 아니라, 식사 **상황을 이해해 한 곳씩** 제안하는 의사결정형 AI 서비스입니다.
- LLM은 자연어 이해·음식 맞추기·리뷰 적합도·추천 이유 생성에 쓰고, **검색·경로·순위 골격**은 코드가 담당합니다.
- **이동 시간 범위 안**이면 **먹고 싶은 음식 + 리뷰**가 순위를 가르고, 거리·시간은 보조 점수입니다.
- 사용자는 처음 **추천 1개**만 보고, 싫어요 2회 후 **후보 3개(triple)** 또는 조건 재질문으로 이어집니다.
- 지도에서 **여유 시간·도보/차량을 바꾸면 검색 반경이 동적으로 넓어지고**(시간 기반), 식당을 자동 재추천합니다.
- 데이터 소스는 MVP에서 **네이버 Local Search + Directions + Place 리뷰 추출** 중심입니다 (초기 Python 검증 파이프라인을 백엔드 도구로 이식).

## 5. AI 서비스 패턴 매핑

| 가이드 패턴 | 머먹 적용 (현재 코드) | 발표 포인트 |
| --- | --- | --- |
| 패턴 1: 생성형 | Gimel 추천 이유, Aleph 음식 맞추기 라벨 | 사용자에게 보이는 문장 품질 |
| 패턴 3: 구조화 출력 | Aleph → Zod 슬롯 JSON (`desiredFoods`, `venuePreference` …) | 후속 Bet/Gimel 로직에 직결 |
| 패턴 4: 복합 폼 | 위치·예산·분위기·동행·이동수단·제외음식 | `questionPresets` + follow-up |
| 패턴 5: 멀티턴 | 누락 슬롯 질문, 싫어요·재추천, refinement | 세션 `sessionId` 유지 |
| 패턴 8: 미니 RAG | 네이버 방문자 리뷰 추출 → 규칙 점수 + Bet LLM | 근거 없으면 주장 생략 |

발표용 한 문장:

> 머먹은 구조화 슬롯·멀티턴 세션·리뷰 근거(RAG)를 **식당 추천 도메인**에 맞게 묶고, 순위는 재현 가능한 코드로 고정했습니다.

## 6. OpenRouter 활용 전략 (실제 기본값)

설정: `server/src/llm/config.js` · env로 역할별 override 가능.

| 역할 | 실제 작업 | 기본 모델 (OpenRouter) | 발표 포인트 |
| --- | --- | --- | --- |
| **Aleph** | 슬롯 추출, **음식 맞추기**(상태→음식 3+비추천) | `anthropic/claude-sonnet-4.6` | 구조화 JSON·한국어 음식 추론 |
| **Bet** | 후보별 **리뷰 적합도** LLM 점수 | `google/gemini-2.5-flash` | 랭킹 보조(규칙이 1순위) |
| **Gimel** | 추천 이유 생성 | `anthropic/claude-sonnet-4.6` | 리뷰 fact만 입력 |
| **Orchestrator** | (코드) 세션·에이전트 호출 순서 | env: `google/gemini-2.5-flash-lite` | **현재 구현은 LLM supervisor가 아닌 deterministic coordinator** |
| **Fallback** | `queryFallback.js`, 규칙 enrich | 코드 | LLM/API 실패 시에도 데모 지속 |

발표 문장:

> OpenRouter로 **Aleph(이해)·Bet(리뷰 점수)·Gimel(설명)** 에 서로 다른 모델을 붙였고, Orchestrator는 안정적인 **코드 파이프라인**으로 동작합니다.

## 7. 시스템 구조

### Frontend (`client/`)

- Vite + Svelte 5, 모바일 우선
- 자연어 입력, GPS / IP 추정 / 수동 위치 검색
- 추가 질문 pill 버튼 (`QuestionForm` + `questionPresets`)
- **작동 로그** (`ActivityStatusBar`) — 기본 접힘, 0.5초 progress 폴링
- 지도: 출발·도착·경로 맞춤 뷰, **여유 시간·도보/차량 이동 가능 원**, 변경 시 **자동 재추천**
- 좋아요 / 싫어요 피드백, 좋아요 식당 로컬 저장

### Backend (`server/`)

- Express, Zod schema (`shared/contracts/schemas.js`)
- 세션 저장 + `GET /api/sessions/:id/progress`
- 네이버 어댑터: Local Search, Directions, 리뷰 추출 (`naverReviewExtractor.js`)
- **검색 반경 = 여유시간 기반 동적 계산** (`shared/contracts/travelRange.js`, 프론트 원과 동일 공식)
- 오류 코드: `GEO_REQUIRED`, `NO_RESULTS`, `SESSION_EXPIRED` 등

### Agent flow

```text
Client
  → POST /api/sessions (progress용 sessionId)
  → POST /api/recommendations { query, location, sessionId }
  → Orchestrator (코드)
      → Aleph (슬롯 / 질문 / 음식 맞추기)
      → [questions] 또는 Bet
      → Bet: 검색 → 경로 → 리뷰 enrich → LLM 리뷰 점수 → rankCandidates
      → Gimel: Top N 추천 이유
  → Client (results | questions)
```

역할:

| Agent | 하는 일 |
| --- | --- |
| **Orchestrator** | 세션, progress 로그, Aleph→Bet→Gimel 순서, 피드백·triple 표시 |
| **Aleph** | 자연어→슬롯, follow-up, **음식 마스터 카탈로그** 기반 음식 맞추기 |
| **Bet** | 네이버 검색·경로·리뷰·**deterministic ranking** + Bet LLM 보조 |
| **Gimel** | 리뷰·메타만으로 grounded reason |

## 8. 기술 차별점 (현재 MVP)

| 항목 | 내용 |
| --- | --- |
| Bounded harness | Aleph / Bet / Gimel 역할 분리, Zod 검증 |
| 음식 카탈로그 | **~160개** 메뉴·의도, 14카테고리 (`foodCatalogData.js`) |
| 음식 맞추기 | “피곤해”“숙취” 등 **상태만**으로 LLM이 음식 3 + 비추천 제안 |
| 랭킹 원칙 | 범위 내: **음식(~48점) + 리뷰(~104점)** >> 거리(≤5) + 시간(≤10) |
| 리뷰 | 규칙(평점·키워드·음식언급) + Bet LLM relevance/sentiment |
| 의도 게이팅 | 술집/해장/카페 — `venueGating` + `foodPreference` |
| 동적 검색 반경 | 지도 **여유시간·이동수단** → `travelRange` 공식으로 반경 확대, 변경 시 자동 재추천 |
| 후보 선별 | 라우팅 전 `candidateSelection`으로 **음식·키워드 적합 후보 우선** 정렬 |
| 좌표 | LLM 프롬프트에 raw lat/lng **미포함**, Bet만 사용 |
| 추천 UX | 1개 → 싫어요 → 1개 → 2회 싫어요 → **3개 비교** 또는 조건 재질문 |
| 투명성 | 하단 **작동 로그**로 Aleph/Bet/Gimel 단계 표시 |

## 9. 랭킹 점수 비중 (발표용 표)

**이동 범위 안** 후보끼리 비교할 때 대략적 가산 비중:

| 묶음 | 최대 점수 | 비율(대략) | 설명 |
| --- | ---: | ---: | --- |
| 먹고 싶은 음식 | 48~52 | ~24% | 이름·카테고리·`foodPreferenceScores` |
| 리뷰 (규칙) | ~59 | ~29% | 평점, 긍정/부정 키워드, 음식 언급 |
| 리뷰 (Bet AI) | 45 | ~22% | relevance(≤30) + sentiment(≤15) |
| 동행·분위기·예산 | 35 | ~17% | context(15) / vibe(10) / budget(10) |
| 이동시간 + 거리 | 15 | ~7% | **후순위·동점 처리** (`timeFit`≤10 / `distanceFit`≤5) |

> 위 5개 묶음 합계 약 202~206점 기준 비율입니다. 이 외에 표에 없는 가산으로 `metadataConfidence`(≤10)·`categorySafety`(≤5)·`venueIntentFit`(≤20, 술집/해장 의도)가 있고, 음식↔리뷰(규칙)는 일부 점수가 겹칩니다.

동점 시: 총점 → **음식+리뷰**(`foodReviewSortScore`) → 이동시간 → 거리.

발표 한 줄:

> “가장 가까운 곳”이 아니라 **“내가 먹고 싶은 음식 리뷰가 맞는 곳”** 이 위로 옵니다.

## 10. 데모 시나리오

### A. 클래식 (슬롯 풀 입력)

```text
친구랑 지금 점심 먹으려고 하는 대학생인데, 한 시간 이내에 다녀올 수 있고 도보로 갈 수 있는 곳 추천해줘. 예산은 12000원 정도고, 너무 시끄럽지 않은 곳이면 좋겠어. 매운 음식은 빼줘.
```

### B. 음식 맞추기 (차별 포인트)

```text
어제 술 마셔서 너무 피곤해
```

→ Aleph이 **음식 맞추기** 질문 (추천 3 + 비추천 태그) → 선택 후 Bet 검색

### C. 술 / 해장 의도

- `친구랑 술마시고 싶다` → bar 검색·랭킹
- `어제 술마셔서 해장` → 해장·국밥, 치킨 감점

### 보여줄 순서

1. 자연어 입력 + 위치(GPS 또는 지역 검색)
2. (선택) 추가 질문 pill / **음식 맞추기** 버튼
3. 하단 **작동 로그** 탭 → Aleph → Bet 검색·리뷰 → Gimel
4. 추천 **1개** + 지도 경로 + 이동 원
5. 추천 이유·provider attribution
6. (선택) 지도에서 **여유시간 늘리기 + 차량** → 검색 반경 확대 + 자동 재추천
7. **싫어요** → 다음 1개
8. 두 번째 싫어요 → **3개 비교** 또는 조건 재질문

데모 멘트:

- “후보를 한꺼번에 다섯 개 보여주지 않고, **결정 피로**를 줄입니다.”
- “순위는 LLM이 아니라 **Bet 랭킹 코드**가 정하고, LLM은 리뷰 적합도와 문장 생성에 씁니다.”
- “리뷰는 네이버에서 **가져올 수 있을 때만** 쓰고, 없으면 이유에서 과장하지 않습니다.”

## 12. 5분 압축 발표안

1. **문제** — 맛집은 많은데 “지금 여기서 이 조건”에 맞는 한 곳 고르기 어렵다.
2. **해결** — 자연어 + 위치 → 슬롯/음식 맞추기 → 네이버 검색·경로·리뷰 → **음식·리뷰 우선** 랭킹 → 이유 생성.
3. **OpenRouter** — 이해(Sonnet)·리뷰 점수(Flash)·설명(Sonnet) 분리.
4. **데모** — 작동 로그 + 1개 추천 + 싫어요.
5. **마무리** — 검증 가능한 추천, MVP 한계(네이버 의존·lint 잔여).

## 13. 평가항목별 발표 문장

**주제 적합성**

> OpenRouter로 Aleph·Bet·Gimel에 역할별 모델을 연결했고, API 키 하나로 대회 요구사항에 맞는 멀티 모델 서비스를 구현했습니다.

**기술 완성도**

> 자연어 입력부터 progress 로그·추천·피드백까지 세션 단위로 이어지며, unit test **163개**가 통과하는 MVP입니다.

**창의성**

> ~160개 음식 카탈로그와 **상태 기반 음식 맞추기**, 규칙+AI 하이브리드 리뷰 점수, **거리보다 음식 적합도**를 우선하는 랭킹이 차별점입니다.

## 15. 예상 질문과 답변 (코드 반영)

### Q1. 왜 OpenRouter인가?

A. 하나의 OpenAI 호환 API로 Claude·Gemini 등을 역할별에 배치할 수 있습니다. Aleph(구조화·음식 추론), Bet(리뷰 배치 점수), Gimel(한국어 설명)에 서로 다른 기본 모델을 둡니다.

### Q2. ChatGPT와 뭐가 다른가?

A. 실제 **네이버 검색·경로·리뷰**와 연결되고, **세션·피드백·순차 추천 UX**가 구현되어 있습니다. 좌표는 구조화 payload로만 다룹니다.

### Q3. 추천 순위는 누가 정하나?

A. **Bet의 `rankCandidates`(deterministic code)** 가 1차입니다. 이동 **시간 예산 안**이면 **음식 적합도·리뷰(규칙+LLM)** 가 거리·시간보다 훨씬 큽니다. Bet LLM은 보조 점수입니다.

### Q4. 가까운 곳이 항상 1등인가?

A. 아닙니다. 범위 안에서는 **고기를 원할 때 가까운 치킨보다 먼 고깃집**이 올라갈 수 있도록 가중치를 설계했습니다.

### Q5. 음식 종류는 어떻게 아나?

A. **~160개 마스터 카탈로그**와 검색·랭킹 키워드가 공유됩니다. 상태만 있을 때는 Aleph LLM **음식 맞추기**로 3개를 제안합니다.

### Q6. 리뷰는 어떻게 쓰나?

A. 네이버 Place에서 리뷰를 추출하고, **평점·키워드·원하는 음식 언급**으로 규칙 점수를 매긴 뒤, Bet LLM이 적합도·감성을 추가합니다. Gimel은 그 fact로만 이유를 씁니다.

### Q7. Orchestrator도 LLM인가?

A. **현재 MVP는 코드 기반 coordinator**입니다. 세션·progress·에이전트 호출 순서를 관리하며, env에는 orchestrator용 모델 슬롯이 있으나 핵심 경로는 deterministic입니다.

### Q8. Kakao도 쓰나?

A. **현재 MVP는 네이버 Local + Directions + Place 리뷰** 중심입니다. 계획서의 Kakao adapter는 이 브랜치 범위 밖이거나 미연동입니다.

### Q9. 위치는 LLM에 들어가나?

A. **raw lat/lng는 LLM에 넣지 않습니다.** Bet에서 검색·경로, Gimel에는 거리·시간·주소·카테고리·리뷰만 전달합니다.

### Q10. 무박 2일에 다 했나?

A. 핵심 UX(입력·질문·음식 맞추기·추천·피드백·지도·로그)는 동작합니다. **lint 12건(unused-var)**, E2E 전면 재검증, 운영 배포는 후속입니다.
