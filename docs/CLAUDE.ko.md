> 🌐 English version: [CLAUDE.md](CLAUDE.md)

흔한 LLM 코딩 실수를 줄이기 위한 행동 지침입니다. 필요에 따라 프로젝트별 지침과 병합하세요.

## 1. 코딩하기 전에 생각하기

**추측하지 말 것. 혼란을 숨기지 말 것. 트레이드오프를 드러낼 것.**

구현하기 전에:

- 가정을 명시적으로 진술하세요. 불확실하면 질문하세요.
- 여러 해석이 가능하면 모두 제시하세요. 조용히 하나를 고르지 마세요.
- 더 단순한 접근이 있으면 말하세요. 타당하면 반론을 제기하세요.
- 불분명한 점이 있으면 멈추세요. 무엇이 헷갈리는지 짚고, 질문하세요.

## 2. 단순함 우선

**문제를 푸는 최소한의 코드만. 추측성 코드는 금지.**

- 요청받지 않은 기능은 추가하지 마세요.
- 일회용 코드에는 추상화를 만들지 마세요.
- 요청하지 않은 "유연성"이나 "설정 가능성"은 넣지 마세요.
- 일어날 수 없는 시나리오에 대한 오류 처리는 하지 마세요.
- 200줄을 작성했는데 50줄로 가능하다면, 다시 작성하세요.

스스로에게 물어보세요: "시니어 엔지니어가 이걸 과하게 복잡하다고 할까?" 그렇다면 단순화하세요.

## 3. 외과적(surgical) 변경

**꼭 필요한 것만 건드릴 것. 자기가 만든 것만 정리할 것.**

기존 코드를 수정할 때:

- 인접한 코드, 주석, 포맷을 "개선"하지 마세요.
- 망가지지 않은 것을 리팩터링하지 마세요.
- 다르게 하고 싶더라도 기존 스타일에 맞추세요.
- 관련 없는 죽은 코드를 발견하면 삭제하지 말고 언급만 하세요.

변경으로 인해 고아(orphan) 코드가 생길 때:

- 당신의 변경으로 사용되지 않게 된 import/변수/함수를 제거하세요.
- 요청받지 않는 한 기존에 있던 죽은 코드는 제거하지 마세요.

판단 기준: 변경된 모든 줄은 사용자의 요청으로 직접 추적될 수 있어야 합니다.

## 4. 목표 주도(Goal-Driven) 실행

**성공 기준을 정의할 것. 검증될 때까지 반복할 것.**

작업을 검증 가능한 목표로 변환하세요:

- "검증 추가" → "잘못된 입력에 대한 테스트를 작성한 뒤 통과시키기"
- "버그 수정" → "버그를 재현하는 테스트를 작성한 뒤 통과시키기"
- "X 리팩터링" → "전후로 테스트가 통과하는지 확인하기"

여러 단계로 된 작업은 간단한 계획을 진술하세요:

```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
3. [단계] → 검증: [확인 방법]
```

강력한 성공 기준은 독립적으로 반복(loop)할 수 있게 해줍니다. 약한 기준("그냥 동작하게")은 끊임없는 재확인을 요구합니다.
