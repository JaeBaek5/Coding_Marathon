## Slide 3 — 한 줄 소개 / 솔루션

### 자연어 + 위치 → 한 곳씩 추천

```text
사용자 자연어 + 위치
  → 상황 이해(슬롯/음식 맞추기)
  → 네이버 검색·경로·리뷰
  → 음식·리뷰 우선 랭킹
  → 추천 1곳 + 이유 + 지도
```

- 처음엔 **1곳만** → 싫어요 → 다음 1곳 → 2회 후 **3곳 비교**

## Slide 4 — OpenRouter 활용 (핵심 차별)

### 작업마다 다른 모델 (역할별 라우팅)

| 역할 | 작업 | 기본 모델 |
| --- | --- | --- |
| **Aleph** | 슬롯 추출 + 상태→음식 맞추기 | `anthropic/claude-sonnet-4.6` |
| **Bet** | 후보별 리뷰 적합도 점수 | `google/gemini-2.5-flash` |
| **Gimel** | 추천 이유 생성 | `anthropic/claude-sonnet-4.6` |

발표 멘트:
> "OpenRouter는 **API 키 하나로 작업마다 최적 모델**을 붙이는 라우팅 계층입니다."

## Slide 5 — 아키텍처 (에이전트 흐름)

```text
Client
  → POST /api/sessions        (progress용 sessionId)
  → POST /api/recommendations  { query, location, sessionId }
  → Orchestrator (코드)
      → Aleph  (슬롯 / 질문 / 음식 맞추기)
      → [질문] 또는 Bet
      → Bet    (검색 → 경로 → 리뷰 enrich → LLM 리뷰점수 → rankCandidates)
      → Gimel  (Top N 추천 이유)
  → Client (results | questions)
```

- **LLM**: 이해 · 음식 맞추기 · 리뷰 적합도 · 이유
- **코드**: 검색 · 경로 · 랭킹 골격 (재현 가능)

## Slide 6 — 차별점 1: 상태 기반 "음식 맞추기"

### "어제 술 마셔서 피곤해" → 음식 3개 추천

- **~160개** 음식 마스터 카탈로그 / **14** 카테고리
- 메뉴를 안 말해도 **상태만으로** 추천 3 + 비추천 제안
- 검색·랭킹이 같은 카탈로그 키워드를 공유

발표 멘트:
> "사용자가 '뭐 먹지'를 모를 때, **상태를 음식으로 번역**합니다."

---

## Slide 7 — 차별점 2: 음식·리뷰 우선 랭킹

### 가장 가까운 곳 ≠ 1등

| 묶음 | 최대 | 비율 |
| --- | ---: | ---: |
| 먹고 싶은 음식 | 48~52 | ~24% |
| 리뷰 (규칙: 평점·키워드·음식언급) | ~59 | ~29% |
| 리뷰 (Bet AI: relevance+sentiment) | 45 | ~22% |
| 동행·분위기·예산 | 35 | ~17% |
| 이동시간 + 거리 | 15 | ~7% |

발표 멘트:
> "**이동 범위 안**이면, 가까운 치킨보다 **먹고 싶은 고깃집**이 위로 옵니다."

---

## Slide 8 — 차별점 3: 동적 검색 반경 + 리뷰 근거(RAG)

### 지도를 바꾸면 검색이 따라온다

- 지도에서 **여유시간·도보/차량** 변경 → `travelRange` 공식으로 **반경 확대** → **자동 재추천**
- 라우팅 전 `candidateSelection`이 **음식·키워드 적합 후보 우선** 선별
- 리뷰는 네이버에서 **가져온 것만** 사용, 없으면 이유에서 과장 없음 (mini-RAG)

## Slide 9 — 데모 시나리오

### A. 풀 플로우
```text
친구랑 지금 점심. 1시간 이내 도보. 예산 12000원. 조용한 곳. 매운 거 빼줘.
```

### B. 음식 맞추기 (강추)
```text
어제 술 마셔서 너무 피곤해
```

보여줄 것:
1. 입력 + 위치 → 2. 하단 **작동 로그**(Aleph→Bet→Gimel) → 3. 추천 1곳 + 지도 경로/이동 원 → 4. 싫어요 → 다음 → 5. 3곳 비교

## 부록 A — 예상 질문 빠른 답변

- **순위는 누가?** → Bet의 `rankCandidates`(코드)가 1차, Bet LLM은 보조.
- **가까운 곳이 1등?** → 아니오. 범위 안에서 음식·리뷰 우선.
- **Orchestrator도 LLM?** → 현재 MVP는 코드 coordinator.
- **위치는 LLM에?** → raw 좌표 미포함. Bet 검색/경로에만 사용.
- **Kakao?** → 현재 네이버 중심.
