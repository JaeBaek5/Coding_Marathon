# 네이버 맛집 추천 파이프라인 — 전체 설명

## 지금 쓰는 파일

- **`naver_nearby_review_test.py`** — 전체 로직이 들어있는 메인 스크립트 (검색 → place_id 변환 → 리뷰/사진/메뉴 추출 → 저장)
- **`.env`** — API 키 보관 (`NAVER_CLIENT_ID`, `NAVER_CLIENT_SECRET`, `OPENROUTER_API_KEY`, `MODEL`)
- (`1.py`는 이 작업 전에 만든 "리뷰만 보는" 단독 실험 스크립트로, 지금 메인 흐름에서는 사용하지 않음)

## 실행

```
python naver_nearby_review_test.py "전남 순천 용당동" 3
```

첫 번째 인자는 위치, 두 번째 인자는 무작위로 뽑을 가게 수(기본 3개). 결과는 콘솔에 출력되고, 가게별로 `data/places/{place_id}.json` 파일에 저장된다.

---

## 전체 흐름 한눈에 보기

```
[1] 위치 검색       네이버 지역검색 API           →  가게 이름 + 주소 후보 (최대 5개)
[2] ID 변환         m.search.naver.com 통합검색    →  이름+주소 → place_id (네이버 내부 식별자)
[3] 리뷰 추출       m.place.naver.com 방문자리뷰    →  place_id → 리뷰 텍스트
[4] 사진 분류       m.place.naver.com __APOLLO_STATE__ →  대표사진 / 메뉴판 / 음식사진 3장
[5] 메뉴판 읽기     OpenRouter Vision LLM          →  메뉴판 사진 → 메뉴명/가격 JSON
[6] 저장            로컬 디스크                     →  data/places/{place_id}.json
```

전부 `naver.com` 도메인 + OpenRouter API만 쓰고, 식당의 외부 홈페이지나 제3자 사이트 주소는 전혀 쓰지 않는다.

## [1] 위치 검색 — `search_nearby_restaurants()`

```
GET https://openapi.naver.com/v1/search/local.json
Headers: X-Naver-Client-Id, X-Naver-Client-Secret
Params:  query="{지역명} 맛집", display=5
```

응답으로 가게 이름·주소·카테고리·좌표(mapx/mapy)를 받는다.

**주의할 점**
- 응답 헤더의 인코딩이 `ISO-8859-1`로 잘못 선언되어 있어서, 받은 직후 `r.encoding = "utf-8"`을 강제해야 한글이 깨지지 않는다.
- 이 API는 **place_id를 주지 않는다.** `link` 필드도 비어있거나 제3자 예약 사이트 주소라 못 쓴다. → 2단계가 필요한 이유.

가게가 여러 개 나오면 `random.sample()`로 요청한 개수만큼 무작위로 뽑는다.

## [2] place_id 변환 — `resolve_place_id()`

네이버 지도 내부 검색 API(`map.naver.com/p/api/search/allSearch`)는 캡차(ncaptcha)로 막혀 있어서 직접 호출이 막혔다. 대신 **모바일 통합검색**(`m.search.naver.com`)을 쓴다. 이 페이지는 검색어와 일치하는 가게가 있으면 결과 HTML 안에 네이버 플레이스 링크를 직접 박아서 내려준다.

```
GET https://m.search.naver.com/search.naver
Params: query="{가게이름} {주소 일부}"
```

HTML 안에서 이런 패턴을 정규식으로 찾는다:

```python
re.search(
    r"m\.place\.naver\.com/(?:place|restaurant|hairshop|beauty|hospital|accommodation|cafe)/(\d+)",
    text,
)
```

**시행착오**
- 처음엔 단순히 `place/(\d+)`만 찾았는데, 검색결과에 같이 섞여 나오는 제3자 예약사이트 링크(`tabling.co.kr/place/677ccea2...`)에도 `place/`가 들어있어서 엉뚱한 값(677)을 집어온 적이 있었다. → `m.place.naver.com` 도메인을 명시해서 해결.
- 네이버 플레이스 링크가 항상 `/place/숫자`인 건 아니고, 업종에 따라 `/restaurant/숫자/home`, `/cafe/숫자/home` 등으로도 나온다. → 업종 경로를 전부 허용하도록 alternation 처리.
- 가게 이름이 흔하거나 검색어 조합이 애매하면 통합검색 결과에 매칭되는 플레이스 카드가 없어서 못 찾는 경우도 있다(실패율 대략 10~30%). 이때는 스킵하고 다음 후보로 넘어간다.

## [3] 리뷰 추출 — `fetch_naver_reviews()`

```
GET https://m.place.naver.com/{업종}/{place_id}/review/visitor
```

`업종`을 미리 알 수 없으니 `restaurant / place / hairshop / beauty / hospital / accommodation / cafe`를 순서대로 시도해서, 처음으로 `200`이 오고 `__APOLLO_STATE__`가 포함된 응답을 쓴다.

### `__APOLLO_STATE__`란?

응답 HTML 안에 이런 스크립트가 박혀있다:

```html
<script>window.__APOLLO_STATE__ = { ...아주 큰 JSON... }; (뒤에 다른 스크립트/CSS가 바로 이어짐)</script>
```

네이버가 GraphQL 클라이언트(Apollo)용으로 서버에서 미리 채워 내려보낸 캐시 데이터다. 리뷰, 작성자, 평점, 가게 정보, 사진, 메뉴 등이 전부 `{"타입:id": {...}}` 형태로 평탄화돼 섞여 있다.

### JSON 파싱 시행착오

처음엔 정규식으로 `{...}`의 끝을 잡으려 했는데(`\{.*?\}\s*;</script>` 또는 그리디 `\{.*\}`), JSON 뒤에 다른 코드가 바로 붙어있어서 끝 위치를 못 찾고 `json.JSONDecodeError`(Extra data)가 계속 발생했다.

**해결**: 시작 위치(`{`)만 찾고 `json.JSONDecoder().raw_decode()`를 쓴다. 이 함수는 완전한 JSON 값 하나를 읽으면 멈추고, 뒤에 남는 잉여 텍스트는 그냥 무시한다.

```python
idx = text.find("__APOLLO_STATE__")
brace_start = text.find("{", idx)
state, _ = json.JSONDecoder().raw_decode(text, brace_start)
```

### 리뷰만 골라내기

`__typename`에 `"Review"`가 포함되고 `body`(본문)가 있는 객체만 골라낸다.

```python
for v in state.values():
    if "Review" in v.get("__typename", "") and v.get("body"):
        reviews.append({author, rating, date, body})
```

작성자는 `Review` 객체가 `User:xxx` 참조(`__ref`)만 갖고 있는 경우가 있어서, `nickname`/`name`을 가진 객체들을 미리 `id → 닉네임` 딕셔너리로 만들어두고 역참조로 매칭한다.

### 한글 인코딩 관련 — 실제로는 안 깨짐

디버깅 중 콘솔에 `name: "�����̰���"`처럼 깨진 글자가 보여서 인코딩 문제라고 의심했는데, 실제로는 **데이터 자체는 올바른 UTF-8**(`"상하이가든"`)이었고 Windows 터미널(cp949)이 출력을 못 그려서 깨진 것처럼 보인 것뿐이었다. 파일로 저장해서 확인하면 정상이다. 다만 `requests`가 응답 인코딩을 잘못 추측(`ISO-8859-1`)하는 경우가 있어서, 받은 직후 항상 `r.encoding = "utf-8"`을 강제하는 습관을 들였다.

## [4] 사진 분류 — `fetch_naver_photos()`

같은 `__APOLLO_STATE__` 안에 `PlaceDetailTopPhotoItem`이라는 타입의 객체들이 있는데, 네이버가 이미 각 사진의 `title`로 앨범 카테고리를 매겨놨다. 직접 확인한 예시(오니크베이크하우스):

| id | type | title |
|---|---|---|
| business_1~5 | business | "오니크베이크하우스" (업주가 등록한 사진, 가게 이름이 title로 들어옴) |
| visitor_1 | visitor | "내부" |
| visitor_2 | visitor | "음식·음료" |
| visitor_3 | visitor | "아메리카노" (구체적 메뉴 이름) |
| visitor_4 | visitor | "외부" |
| visitor_5 | visitor | "메뉴판" |

이 `title`을 그대로 분류 기준으로 쓴다. **이건 LLM이 매번 사진을 보고 판단하는 게 아니라, 네이버가 이미 매겨둔 태그를 코드 규칙으로 분류한 것**이라 빠르고 무료다.

- **대표 사진(`main_photo`)**: `type == "business"`인 사진 중 첫 번째. 검색결과/지도에 노출되는 대표 이미지는 `PlaceDetailBase`에 별도 필드로 있는 게 아니라, 업주 등록 사진 앨범에서 번호(`no`)가 가장 작은 사진이 그 역할을 한다. dict 순회 순서가 `no` 순서와 같아서 첫 매칭이 곧 그 사진이다.
- **메뉴판(`menu_board`)**: `title`이 `"메뉴판"` 또는 `"메뉴"`인 사진. 없으면 `None` → 5단계(Vision LLM) 자체를 스킵해서 비용을 아낀다.
- **음식 사진 3장(`food`)**: 대표/메뉴판/외부/내부로 분류되지 않은 나머지(예: "음식·음료", 구체적 메뉴명). 앨범에 3장이 안 되면, 같은 페이지의 `Menu` 객체(가게가 메뉴 등록 시 올린 `{name, price, images}`)에서 보충한다.

리뷰 페이지(`/review/visitor`)가 아니라 `/home` 페이지를 한 번 더 요청해서 가져온다 — 단, `__APOLLO_STATE__`는 어느 서브페이지를 열든 같은 내용을 담고 있어서 `/home`만 호출해도 사진·메뉴·리뷰 데이터가 전부 들어있다(실제 확인함).

## [5] 메뉴판 사진 읽기 — `extract_menu_from_photo()`

메뉴판은 사진일 뿐이라 그 자체로는 "메뉴명·가격" 데이터가 아니다. OCR 대신, 이미지를 직접 이해할 수 있는 OpenRouter의 멀티모달 모델(`.env`의 `MODEL`, 기본값 `anthropic/claude-sonnet-4.5`)에게 이미지 URL을 그대로 보여주고 읽게 한다.

```python
vision_client.chat.completions.create(
    model=VISION_MODEL,
    messages=[{
        "role": "user",
        "content": [
            {"type": "text", "text": "이 메뉴판 사진을 읽고 메뉴 이름과 가격을 JSON 배열로 추출해줘..."},
            {"type": "image_url", "image_url": {"url": image_url}},
        ],
    }],
)
```

모델 응답이 ` ```json ... ``` ` 코드블록으로 감싸져 오는 경우가 있어서, 파싱 전에 정규식으로 백틱을 벗겨낸다. 글자를 못 읽으면 빈 배열 `[]`을 반환하도록 프롬프트에 명시해뒀다.

**실측 결과** (이자카야 메뉴판 사진): 사시미·튀김·세트 메뉴 16개를 가격까지 정확히 읽어냄 (예: `{"name": "모듬 사시미", "price": "45,000-60,000"}`).

메뉴판이 없는 가게는 이 단계를 건너뛰므로, **Vision LLM 호출(=비용)은 메뉴판 사진이 실제로 있을 때만 발생**한다.

## [6] 저장 — `save_place_data()`

```python
DATA_DIR = "<프로젝트 폴더>/data/places"

def save_place_data(place_id, data):
    os.makedirs(DATA_DIR, exist_ok=True)
    json.dump(data, open(f"{DATA_DIR}/{place_id}.json", "w", encoding="utf-8"),
              ensure_ascii=False, indent=2)
```

가게 하나당 `data/places/{place_id}.json` 한 파일로 저장된다.

| 키 | 내용 |
|---|---|
| `placeId` | 네이버 플레이스 ID |
| `name`, `category`, `address` | 검색 API에서 받은 기본 정보 |
| `mainPhoto` | 대표 사진 URL |
| `menuBoardPhoto` | 메뉴판 사진 URL (없으면 `null`) |
| `menuItems` | Vision LLM이 읽은 `[{name, price}]` 배열 (메뉴판 없으면 `[]`) |
| `foodPhotos` | 음식 사진 최대 3장 `[{title, url}]` |
| `reviews` | 방문자 리뷰 목록 (작성자/평점/날짜/본문) |

예시 (`data/places/1256451381.json`, 롯데리아 순천용당점):

```json
{
  "placeId": "1256451381",
  "name": "롯데리아 순천용당점",
  "category": "양식>햄버거",
  "address": "전라남도 순천시 삼산로 102",
  "mainPhoto": "https://ldb-phinf.pstatic.net/.../Y7f2184P-J85WH231byWVjLX.jpg",
  "menuBoardPhoto": null,
  "menuItems": [],
  "foodPhotos": [
    { "title": "음식·음료", "url": "https://pup-review-phinf.pstatic.net/..." },
    { "title": "버거", "url": "https://pup-review-phinf.pstatic.net/..." }
  ],
  "reviews": [ { "author": "hs42", "rating": null, "date": "3.21.토", "body": "..." } ]
}
```

프론트엔드는 이 파일 하나만 읽으면 가게 카드에 필요한 대표 사진·메뉴판·메뉴 정보·음식 사진·리뷰를 한 번에 그릴 수 있고, 네이버 API를 다시 호출하거나 이미지를 직접 처리할 필요가 없다.

## 함수별 책임 정리

| 함수 | 역할 | 의존 |
|---|---|---|
| `search_nearby_restaurants` | 위치 → 가게 후보(이름/주소) | 네이버 지역검색 API |
| `resolve_place_id` | 가게 이름+주소 → place_id | m.search.naver.com |
| `fetch_naver_reviews` | place_id → 리뷰 목록 | m.place.naver.com `__APOLLO_STATE__` |

| `save_place_data` | 위 결과 전부 → JSON 파일 | 로컬 디스크 |

## 한계 및 향후 보강 방향

- place_id 변환(2단계)은 통합검색 결과를 긁는 방식이라 100% 성공률이 아니다. 흔한 상호명이거나 검색어 조합이 애매하면 실패한다. → 계획서에서 언급된 대로, 정적 파싱이 실패할 경우 헤드리스 브라우저(Selenium/Playwright) 기반 추출을 폴백으로 두는 게 안전하다.
- 네이버가 HTML 구조나 `__APOLLO_STATE__` 키 이름을 바꾸면 파싱이 깨질 수 있다.
- 대표 사진을 "type=business 중 첫 번째"로 추정하는 방식이라, 네이버가 사진 정렬 순서를 바꾸면 다른 사진이 잡힐 수 있다.
- 메뉴판이 여러 장(앞면/뒷면 등)인 가게는 현재 첫 번째 메뉴판 사진만 사용한다.
- Vision LLM 추출 결과는 사진 해상도/필기체 메뉴판 등에 따라 정확도가 달라질 수 있으니, 프론트엔드에서는 "추출된 메뉴 정보"라고 표시하고 실제 메뉴판 사진도 같이 보여주는 게 안전하다.
- 검색 API와 Vision LLM 호출 모두 쿼터/비용이 있으므로 대량 호출 시 캐싱이 필요하다.
